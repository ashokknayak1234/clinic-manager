Append-only record of every place where the implementation diverged from the binding

## 2026-11-14

### 1. `next.config.ts` carries two settings the spec snippet does not include

Spec §13.2 prescribes only `reactStrictMode` + the `/api` rewrite. This build adds
`turbopack: { root: process.cwd() }` and `outputFileTracingRoot: process.cwd()`.

Reason: without them, Next resolved the workspace root as `C:\Users\ASHOK` (the directory
above the repository) and dev resources failed to load. Both values pin the root to the
repository and change nothing else.

### 2. Dev server must be opened via `http://localhost:3000`, not `127.0.0.1`

Next 16 blocks cross-origin dev resources, and `127.0.0.1` counts as cross-origin, which
breaks hydration. Operational note recorded in `frontend/README.md`; no config override
(`allowedDevOrigins`) was added because using `localhost` is sufficient.

- `form` was **not** installed. All forms (login, register, profile, filters) use native
  labelled inputs with explicit `name`, `autocomplete` and `inputMode` attributes per §11,
  composed with the shadcn `input`/`label`/`select` primitives. No react-hook-form
  dependency was added.
- shadcn 4.23 with the `radix-nova` style installed `radix-ui`, `cn` (shadcn-ui's
  clsx + tailwind-merge replacement), the `shadcn` CLI package, `next-themes` and `sonner`

  `sonner` and `next-themes` are referenced only by the unused
  `components/ui/sonner.tsx` generated by shadcn.
- Follow-up (same day): the installed-but-unused primitives were wired into the product so
  they are no longer dead code — `avatar` (sidebar account row, topbar, care team, hero
  cluster card), `dropdown-menu` (topbar account menu: Profile / Sign out), `textarea`
  (profile address field), and `sonner` (Toaster mounted in `AppProviders`; the booking
  confirmation toast reuses the screen's existing §7 sentence verbatim). `card`, `badge`,
  `progress`, `separator` and `tabs` remain installed per §8.1 but have no §6 slot that

- Pinned runtime versions match the spec exactly: `next@16.4.6`, `react@19.3.1`,

Consequences:

### 5. Backend register bug: every new account becomes RECEPTIONIST

`backend/app/repositories/users.py` hardcodes `role_id = 4` (RECEPTIONIST) when creating a
user, so registration never produces a PATIENT (role 3). Spec §6.8 relies on "the backend
always creates a PATIENT".

Because `backend/**` is read-only, this is **documented, not fixed**. The client keeps the
spec redirect to `/dashboard`. Consequence: the PATIENT sidebar (Dashboard, Doctors,
Appointments, Prescriptions, Invoices, Profile) could not be verified end-to-end; the
staff-role navigation (§12.4 DOCTOR/ADMIN/RECEPTIONIST items) was verified instead.

### 6. Contrast limitation: binding palette values sit below WCAG AA at some pairings

Spec §11 asserts `ink-muted #71757F` on white is ≈4.6:1 — confirmed: **4.61**. However the
same token fails 4.5:1 on the spec's own surfaces:

| Foreground | Background | Measured | Where |
| --- | --- | --- | --- |
| `#71757F` ink-muted | `#F9FAFB` marketing | 4.41 | nav links, logo descriptor |
| `#71757F` ink-muted | `#F7F7F9` panel | 4.31 | portal shell copy |
| `#71757F` ink-muted | `#EFF7FF` primary-50 | 4.26 | login demo-alert body |
| `#9CA3AF` ink-faint | `#FFFFFF` surface | 2.54 | captions, footer column heads |
| `#FFFFFF` white | `#2589F5` primary-500 | 3.51 | hero blue card text (§6.2.2 "white text") |

One real markup bug was fixed: the hero blue card used `text-white/80`, which composits to
`#D3E7FD` on `#2589F5` = **2.78**; it now uses solid white (3.51). Lighthouse
`color-contrast` no longer flags that card.

Token values were **kept exactly as bound** (owner direction): no hex was changed, and
`app/globals.css` remains the only source of colour. Lighthouse on `/` (desktop,
production build) scores **95 accessibility / 100 best-practices / 100 SEO**, meeting the
§13.6 a11y ≥95 gate; `color-contrast` remains the only failing audit, caused by the
binding values above. Resolving it needs an owner decision: darken `ink-muted`/`ink-faint`
or restrict them to ≥18px text — both would deviate from §5.1/§6, so it was not done
unilaterally.
